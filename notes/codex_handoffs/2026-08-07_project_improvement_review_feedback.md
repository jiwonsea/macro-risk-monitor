## 총평

핵심 문제 제기는 타당하다. 다만 "블로그가 본체 엔진을 재구현한다", "현재 데이터로 v2 P13이 충족됐다", "draft 두 개를 승격하면 수동 채점이 해결된다"는 세 결론은 근거보다 강하다.

가장 큰 결함은 코드 중복이 아니라 다음 세 의미가 한 CSV에 섞여 있다는 것이다.

- 예측 사건이 발생했는가
- 그 사건이 논지를 지지하는가
- 논지 전체가 tail에서 base로 바뀌었는가

9적중과 논지 약화가 공존한 직접 원인은 이 세 층을 분리하지 않은 데 있다.

## 1. 항목별 판정

### #1 — 블로그 채점이 본체 엔진을 재구현 · **MODIFY**

**근거가 결론을 지지하는가.** CSV 열 밀림은 실제 검증 부재를 입증한다. 그러나 scorecard가 Trigger·Threshold를 "손으로 재구현"한다는 결론은 과장이다. 본체는 연속 상태를 RED/YELLOW/GREEN으로 분류하고, scorecard는 시점 고정 예측을 적중/빗나감으로 채점한다.

**처방 적정성.** 1-A는 적정, 1-B는 과잉, 해시는 수정 필요.

**대안/반박.** 독립 `ScoreItem`과 validator를 만든다. 기존 trigger parser는 비교식 파싱 부분만 재사용할 수 있다. Git commit 자체가 불변 스냅샷이므로 네 열의 별도 해시보다 `registered_commit`을 저장하고 `git show <commit>:<path>`와 비교하는 편이 감사 가능하다. 오타 수정은 원본 불변 + correction ledger 방식으로 처리한다.

### #2 — vintage 규칙 부재 · **ADOPT**

**근거가 결론을 지지하는가.** 빈티지 선택에 따라 P4 판정이 뒤집힐 수 있었고 payroll 개정은 논지 해석을 크게 바꿨다. 현재 `Reading.as_of`만으로는 관측기간·발표일·빈티지를 구분할 수 없다.

**처방 적정성.** 규칙은 MODIFY, 두 값 분리는 적정, ALFRED 자동화는 당장 과잉.

**대안/반박.** 모든 지표에 무조건 first print를 적용하지 말고 **예측 대상별로 사전 선언**한다. "발표 결과 예측"은 first print로 채점하고, "경제 상태/논지 평가"는 current vintage도 별도로 평가한다. `observation_period`, `released_at`, `retrieved_at`, `vintage_policy`, `actual_first_print`, `actual_current`을 기록한다. 지금 규모에서는 발표 당일 원자료 스냅샷으로 충분하며 ALFRED는 반복 채점·백테스트가 시작될 때 도입한다.

### #3 — v2 기준 오염 · **MODIFY**

**근거가 결론을 지지하는가.** v2가 P1~P4 발표 후 작성된 것은 사실이고 오염 가능성을 만든다. 그러나 파일 시각만으로 실제 결과 맞춤을 입증할 수는 없다. 특히 v2는 적중을 보존하기보다 기존 기준을 더 어렵게 만든다.

**대안/반박.** `written_on`, `known_results`, `origin`, `prospective_only`를 기록한다. **"오염"과 "결과 노출"을 구분**해야 한다. 제3자도 결과를 이미 알기 때문에 blind 재작성은 불가능하다. 대신 결과값을 숨긴 과거 기간에 규칙을 적용하거나, 향후 관측에만 적용해 검증한다.

**근거가 결론을 지지하는가.** P5~P9가 맞으면서 원글의 노동수요 해석이 약해진 것은 수준 기준이 논지 변화에 둔감함을 보여준다.

### #5 — 본문 수치 verifier · **MODIFY**

**근거가 결론을 지지하는가.** 본문 숫자 검증이 수작업이고 기존 verifier 개념을 활용할 수 있다는 지적은 맞다. 다만 현재 verifier는 블로그 검증기로 그대로 쓸 수 없다.

**처방 적정성.** 별도 어댑터/코어 추출이 적정.

**대안/반박.** 숫자 추출·정규화·허용오차 비교를 작은 공용 모듈로 분리하고, 본체와 블로그가 각각 anchor provider를 제공한다. 연도·절 번호·날짜·범위·단위 환산을 구분하지 않으면 오탐이 과도하다. allowlist는 수작업이지만 `value + unit + claim + source_url + as_of` 구조로 만들면 출처 없는 숫자의 유입을 막는 감사 장부가 된다.

### #6 — draft 가설 승격 · **REJECT**

**근거가 결론을 지지하는가.** frontmatter가 존재하지 않는 thesis 이름을 가리키고 자동 파이프라인에 연결되지 않는다는 사실은 맞다. 하지만 **수동 채점의 원인이 draft 상태라는 결론은 틀렸다.**

**처방 적정성.** 6-A는 현재 부적정.

**대안/반박.** 두 draft 자체에 percentile 계산, gating, 파생 source, cross-thesis 조합 등 승격 차단 사유가 명시돼 있다. one-shot 예측을 연속 위험 트리거로 옮겨도 scorecard 채점은 대체되지 않는다. frontmatter에 `thesis_status: draft` 또는 draft 경로를 명시하고 **참조 무결성만** 검사한다. 승격은 기존 BLOCKING 해결 후 별도 작업으로 한다.

### #7 — 발표일 오기 / 저장소 위생 · **MODIFY**

**근거가 결론을 지지하는가.** 날짜 오기는 판정 결과에는 영향이 없었지만 사전등록의 시간 무결성을 훼손할 수 있다. `_to_delete/` ignore는 적절한 위생 조치다.

**처방 적정성.** 7-A의 "낮음"은 **과소평가**.

**대안/반박.** 중요도는 중간 이상이다. 다만 전체 일정 생성기를 먼저 만드는 것보다, 채점 시 공식 release URL과 실제 `released_at`을 필수 기록하고 `registered_at < released_at <= scored_at`을 검사하는 것이 작고 직접적이다. 이후 반복 일정에 한해 공식 캘린더 수집을 자동화한다.

## 2. 세부 질문에 대한 답

### 1번 — 통합과 해시

blog/와 본체를 하나의 데이터 모델로 통합하는 것은 권하지 않는다. 두 시스템은 대상이 다르다.

| 구분 | 본체 trigger | 블로그 scorecard |
|---|---|---|
| 질문 | 지금 위험 상태는 무엇인가 | 사전 예측이 맞았는가 |
| 시간 | 반복 관측 | 지정된 해소 시점 |
| 결과 | RED/YELLOW/GREEN/UNKNOWN | 적중/빗나감/판정불가/미도래 |
| 기준 변경 | 운영 임계치 업데이트 가능 | 등록 후 불변이어야 함 |
| 개정치 | 최신 상태가 흔히 중요 | 사전 선언한 vintage가 중요 |

따라서 1-A만 먼저 하는 것이 비용 대비 낫다. 1-B를 하더라도 엔진 전체를 연결하지 말고 비교식 parser만 공유해야 한다. `engine/trigger.py`는 단일 숫자 비교와 범위만 지원하므로 **P2, P4 v2, P7~P10, P13~P15 같은 복합 조건을 표현하지 못한다.**

별도 해시는 작동하지만 Git과 기능이 중복되고 correction workflow를 불편하게 한다. 권장 계약:

- `registered_commit`으로 원본을 고정
- validator가 현재 네 필드를 해당 commit과 비교
- 오류는 원본 수정 대신 `correction_reason`, `corrected_on`, `supersedes`로 추가
- 원본 오류와 수정된 운영 기준을 모두 보존

### 2번 — first print와 current vintage

둘 중 하나를 모든 경우에 선택하면 정보가 손실된다.

- "7월 고용보고서에서 payroll이 얼마로 발표되는가"는 **first print**가 채점 대상이다.
- "당시 노동수요가 실제로 꺾였는가"는 **current vintage**가 논지 평가에 더 적합하다.
- "그때 이용 가능했던 정보로 판단이 합리적이었는가"는 당시 **realtime vintage 전체**가 필요하다.

따라서 적중률은 first print로 고정하되, 논지 평가는 current vintage로 별도 표시하는 **이중 장부**가 가장 정직하다. 지표별 예외를 사후 선택하면 cherry-pick이지만, 예측의 target type에 따라 사전 선언하면 정당하다.

ALFRED는 장기 백테스트에는 가치가 있지만 15개 예측 때문에 바로 의존성을 추가할 필요는 없다. 발표 당일 공식 자료와 원계열 snapshot을 저장하는 방식이 먼저다.

### 3번 — v2 오염 판정

"오염"을 두 단계로 나눠야 한다.

- **EXPOSED**: 작성 전에 해당 결과가 공개됨
- **LIKELY-INFLUENCED**: 규칙의 구체적인 형태가 공개 결과에 적응한 정황이 강함

| ID | 판정 | 이유 |
|---|---|---|
| P1 | LIKELY-INFLUENCED | FOMC 결과와 성명 내용을 본 뒤 OIS·성명 점수 결합안이 작성됐다. 다만 기존 기준의 적중을 보존하는 방향은 아니고 더 엄격한 일반 개선이다. |
| P2 | LIKELY-INFLUENCED | 실제로 위치 테스트와 수식 테스트가 갈렸던 사건을 본 뒤 문구 점수화가 제안됐다. 결과 구조와 직접 대응한다. |
| P3 | LIKELY-INFLUENCED | 3%대라는 넓은 밴드가 손쉽게 적중한 것을 본 뒤 방향+오차 방식으로 바뀌었다. |
| P4 | LIKELY-INFLUENCED | −0.135%p로 기존 −0.15%p 선을 근소하게 통과한 뒤 3개월 모멘텀으로 교체됐다. |
| P5~P9 | 무관 | 7월 결과 공개 전 작성됐다. 과거 수준을 알았다는 것과 대상 결과를 본 것은 다르다. |
| P10 | 무관 | 7월 CPI 발표 전 작성됐다. |
| P11·P12 | 무관 | 8월 평가창 종료 전 작성됐다. |
| P13 | 무관 | 현재 평가 결과를 본 수정이 아니라 v1 논리식의 내부 모순을 고친 것이다. |
| P14 | 무관 | 7월 CPI 발표 전 작성됐다. |
| P15 | 무관 | 8월 평가 종료 전 작성됐다. |

P1~P4도 "부정행위가 입증됐다"기보다 **결과 노출 후 설계되어 독립 검증용으로 쓸 수 없다**는 판정이 정확하다. 파일 시각만으로 의도적 맞춤을 주장할 수는 없다.

3-B는 해결책이 아니다. Codex도 결과를 알고 있기 때문이다. 필요한 것은 기억을 지우는 제3자가 아니라 다음 중 하나다.

- v2를 향후 데이터에만 적용
- 결과를 숨긴 다른 역사적 기간에서 false-positive/false-negative 평가
- 규칙의 입력·변환·임계·평가창을 완전히 수치화한 뒤 동결

### 4번 — P13 적용 여부

**현재 데이터만으로 v2 P13이 형식적으로 충족됐다고 판정할 수 없다.** v2 문구는 다음을 정의하지 않았다.

- "인플레 지속 지표"가 Core PCE YoY인지, 3개월 연율인지, 5y5y인지
- 지속의 임계치
- "노동수요 악화 지표"가 payroll first print인지 개정치인지
- 평가창의 시작·종료
- 계절조정과 빈티지 규칙

따라서 Core PCE 3.29% + payroll −23k는 P13을 충족할 수 있는 **강한 후보 증거**지만, 등록된 실행 가능한 규칙에 따른 판정은 아니다.

더 중요한 의미 구분도 필요하다. 조건이 충족되더라도 바로 "base가 됐다"기보다 **"tail→base 재평가 gate가 열렸다"**로 쓰는 편이 논리적으로 안전하다. 단 한 달의 payroll과 높은 물가만으로 modal scenario 전환까지 자동 결론 내리면 P13이 다시 과도한 기준이 된다.

**결론: 문서의 4-(a)는 방향상 타당하지만 현재 v2 문구를 확대해석했다.**

### 4-A — Brier score

도입 자체는 유효하지만 범위를 제한해야 한다.

- P1처럼 명확한 이항 사건에는 적합하다.
- P2처럼 판정자 재량이 있는 사건에는 부적합하다.
- P13처럼 복합 논지 상태에는 사건 정의를 먼저 고정해야 한다.
- 15개로 신뢰도 곡선이나 예측자 능력을 주장할 수는 없다.
- **서로 강하게 상관된 P5~P9를 독립 5건처럼 평균하면 표본 수를 부풀린다.**

개별 예측의 확률 정직성을 강제하는 용도로는 첫 표본부터 가치가 있다. 통계적 실력 평가에는 장기 누적과 시장·컨센서스 baseline 비교가 필요하다.

### 4-B — 반증 조건

반증 조건은 "기준 하나 추가"에 그칠 수도 있다. 가치가 생기려면 서로 다른 대상을 분리해야 한다.

- 관측 예측: `EMRATIO <= 59.0`
- 메커니즘 주장: 고용 약화의 주원인은 노동공급 축소다
- 반증 조건: payroll 수요가 음전환하거나 광범위한 고용수요 지표가 동반 악화
- 논지 전환 규칙: 인플레 지속과 노동수요 악화가 같은 사전 정의 창에서 동시 발생

이번 scorecard에는 첫 번째만 많았고 나머지가 부족했다.

### 5번 — verifier

기존 `ai/verifier.py`를 그대로 재사용하면 안 된다. 현재 구현의 제약:

- 소수점 또는 %, bp, $, 원, 억, 조 등이 붙은 숫자만 잡는다.
- 날짜, 정수 천명, 범위, 음수 표현, 쉼표 포함 숫자를 충분히 모델링하지 않는다.
- ±5% 근접만 확인하고 숫자가 어떤 주장·단위·출처에 연결되는지는 확인하지 않는다.
- 동일한 값이 다른 의미로 쓰여도 통과할 수 있다.
- 블로그에는 Risk, Verdict, Reading 정답지가 없다.

권장 구조는 "기존 verifier 호출"이 아니라 숫자 검증의 작은 공용 코어를 추출하는 것이다.

1. Markdown에서 숫자와 주변 문맥 추출
2. 단위 및 표현 정규화
3. 블로그 source registry에서 anchor 조회
4. 자동 매칭 실패 항목을 source-backed allowlist와 대조
5. 남은 항목을 실패로 출력

allowlist는 수작업이지만 이득이 남는다. 기존 수작업은 본문 전체를 매번 다시 검색하지만, allowlist는 한 번 검증된 외부 수치를 구조화해 재사용한다. 단, 값만 적는 allowlist는 면죄부가 되므로 출처와 시점을 필수화해야 한다.

### 6번 — draft 승격

**승격하면 안 된다.** 두 draft는 단순히 위치만 잘못된 파일이 아니다. 스스로 다음 차단 사유를 기록하고 있다.

- rolling percentile 미지원
- 3개월 연율 등 계산형 source 미지원
- OIS/futures source 미확정
- pass-through gate와 AND gate 미지원
- 다른 thesis verdict 조합 방식 미정
- 다수 임계치가 UNVERIFIED

또한 one-shot forecast와 continuous trigger 사이에는 다음 손실이 있다.

- 해소일과 발표 빈티지 소실
- 적중/빗나감의 방향성 소실
- 예측 난이도와 확률 소실
- 복합 논지 조건이 단일 상태 색상으로 축약
- 여러 상관 지표가 rule-of-three에서 독립 증거처럼 중복 계산될 위험

따라서 frontmatter 참조 오류만 고치되 draft 상태를 정직하게 표현해야 한다.

### 7번 — 발표일

우선순위가 낮다고 보기 어렵다. 등록 시각과 발표 시각의 순서는 사전등록의 핵심 무결성 조건이다. 다만 "공식 캘린더 자동 생성" 전체를 바로 구축할 필요는 없다. 먼저 각 채점에 다음을 저장하고 검사하는 편이 작다.

- 공식 release URL / 예정 발표 시각 / 실제 발표 시각 / 채점 시각
- `registered_at < actual_released_at <= scored_at`

현재 제안의 "`resolve_on > today`인데 verdict가 있으면 실패"만으로는 부족하다. 공식 발표가 당겨지거나 `resolve_on` 자체가 틀렸을 때 올바른 채점을 오히려 거부하기 때문이다.

## 3. 실제 착수 우선순위

1. **2** — vintage 및 시간 provenance 규칙
2. **7** — 공식 발표 시각 검증
3. **1** — ScoreItem validator와 등록 commit 비교
4. **4** — 관측 예측·메커니즘·논지 전환 규칙 분리
5. **3** — v2 결과 노출 기록 및 prospective-only 선언
6. **5** — 블로그 수치 verifier
7. **6** — draft 참조 정리; thesis 승격은 보류

**하나만 한다면 2번이다.** vintage 정책이 없으면 동일한 사전 기준으로도 판정이 바뀔 수 있기 때문이다. CSV 열 밀림은 validator로 잡을 수 있지만, 어떤 빈티지가 정답인지 정의되지 않은 문제는 문법 검증으로 잡을 수 없다.

단, 구현 단위로는 2번의 필드를 담을 **최소 ScoreItem 스키마**가 함께 필요하다. 이는 1번 전체 통합이 아니라 2번 규칙을 집행하기 위한 얇은 데이터 계약이다.

## 4. 문서가 놓친 결함

### 4.1 예측과 논지의 다대일 관계가 없다

P5~P9가 모두 적중해도 thesis가 약해질 수 있다는 것은 점수 기준이 느슨한 문제만이 아니다. 각 예측이 **어느 주장에 어떤 방향으로 기여하는지** 선언하지 않았기 때문이다. 최소한 `supports_claim`, `evidence_direction`(supports/contradicts/neutral), `weight` 또는 중복 그룹, `thesis_transition_rule`이 필요하다. 그렇지 않으면 적중률은 있어도 논지 업데이트 규칙은 없다.

### 4.2 상관된 예측을 독립 적중으로 센다

P5 EMRATIO, P6 CIVPART, P7 UNRATE는 **동일한 가계조사 항등관계**에 강하게 연결돼 있다. 이를 3개의 독립 적중으로 세면 증거량이 부풀려진다. P5~P9의 "5적중"은 다섯 독립 예측의 성공과 같지 않다. `dependency_group`을 두고 그룹 단위 score도 함께 보여야 한다.

### 4.3 등록 시각이 날짜 단위다

FOMC·경제지표는 같은 날짜 안에서도 발표 전후가 중요하다. `registered_on: 2026-07-28`만으로는 사전등록 여부를 완전히 증명하지 못한다. timezone이 포함된 `registered_at`과 commit hash가 필요하다.

### 4.4 actual이 표시문과 계산 입력을 겸한다

현재 `actual`은 `"3.2% (시간당 $37.62, 전월 +2센트)"` 같은 산문이다. CSV 사고뿐 아니라 자동 재계산도 불가능하다. `actual_value`, `actual_unit`, `actual_display`, `source_url`, `observation_period`, `released_at`, `vintage`로 분리해야 한다.

### 4.5 기준과 채점 코드의 버전이 연결되지 않는다

v2 파일은 있지만 어느 후속 scorecard가 어느 기준 버전을 사용했는지 강제하는 참조가 없다. `criteria_version` 또는 criteria commit을 각 scorecard에 명시해야 한다.

## 5. 역제안 반박

"9적중이 민망해서 채점 체계 탓을 한다"는 해석은 일부 그럴듯하지만 주된 설명은 아니다.

**그럴듯한 부분.** 결과가 9/9가 아니었다면 Brier score나 기준 난이도 문제가 이 정도로 부각되지 않았을 수 있다. P1~P4 결과를 본 뒤 v2를 설계했기 때문에 사후적으로 "이 적중은 쉬웠다"는 서사가 강화됐다. 현재 비판은 적중률의 의미를 낮추므로 자기과신 비판을 선제적으로 방어하는 효과가 있다.

**충분하지 않은 부분.** P13의 논리 반전은 결과와 무관한 객관적 결함이다. CSV 열 밀림과 발표일 오기는 실제 운영 사고다. 빈티지에 따라 P4 판정이 바뀔 수 있다는 문제는 9/9의 미관과 무관하다. P5~P9가 잡지 못한 payroll 음전환·대규모 개정은 scorecard와 원글 논지 사이의 실제 내용 불일치다. **결과가 공개된 뒤 v1을 고쳐 적중을 보존하지 않고, 오히려 v1의 약점을 공개한 점은 단순 자기변호 가설과 맞지 않는다.**

**최종 판정.**

> 이 문서는 9적중을 부끄러워해 채점 자체를 무효화하려는 문서라기보다, 9적중이 "예측 정확도"와 "논지 타당성"이 다른 대상임을 드러낸 뒤 뒤늦게 평가 단위를 바로잡으려는 문서에 가깝다. 다만 그 반작용으로 본체 엔진 통합, Brier score, ALFRED, draft 승격까지 한꺼번에 처방한 부분은 과잉이다.

가장 정직한 공개 표현은 **"9개 관측 예측은 등록 기준상 적중했지만, 이 적중률은 논지 검증 점수가 아니며 상관된 저난도 항목을 포함한다"** 이다.
